# 类比设计：选一个能撑住全文的比喻

## 一、只有一个类比

全文所有章节都挂在同一个类比上。中途换类比，读者要重建一次心智模型——第二次重建时，他已经不想读了。

判断是否"同一个类比"的标准很简单：**能不能用类比里的角色，把最后一节也讲完**。讲不完就说明类比撑不住，换一个更好的，而不是补第二个。

## 二、三类常见失效

| 失效 | 表现 | 后果 |
|---|---|---|
| 太宽泛 | "就像一个系统""就像一条流水线" | 没有具体角色，读者无法在自己经验里定位 |
| 太文学 | "如同星河的潮汐" | 好听但不承载机制，第三段就词穷 |
| 同构点少 | 只有名字像，机制对不上 | 读者用类比推演时会得出错误结论，比不讲更糟 |

## 三、选取流程

### 第 1 步：列出真实系统的"角色清单"

不看材料里的术语，先问：这个系统里有哪些**承担不同职责的角色**？

以 AI 网关为例：

- 发出请求的（客户端，且写法不统一）
- 接收所有请求的入口
- 逐项检查的处理环节（身份、能力、速率、预算、去向）
- 真正干活的执行体
- 多个可替换的上游供给方
- 出问题时接管的后备

### 第 2 步：找读者职业里同构的角色集合

要求：读者**每天真实接触**，不是"听说过"。

| 领域 | 可用类比 | 同构点数量 |
|---|---|---|
| 物流 | 转运中心 / 分拣线 / 报关 | 高（面单、分拣、干线、签收、丢件） |
| 医疗 | 分诊台 / 检验科 / 会诊 | 中高（分诊、转科、复检） |
| 金融 | 清算所 / 授信审核 | 中（授信、轧差、对账） |
| 制造 | 质检工位 / 总装线 | 中 |
| 行政 | 前台登记 / 审批流 | 低（环节太少，撑不住 6 段） |

### 第 3 步：写映射表，**必须写不同构点**

```markdown
| 真实概念 | 类比角色 | 同构点 | 不同构点 |
|---|---|---|---|
| 三种客户端协议 | 三种面单写法 | 格式不同、语义相同、可互转 | 面单写错能人工纠正，协议不兼容直接报错 |
| 网关入口 | 转运中心 | 吃掉上游差异、业务方只需对接一次 | 转运中心会丢件，网关不能丢字节 |
| 上游渠道池 | 多家快递公司 | 成本不同、可随时停运、可切换 | 快递不可"同时用两家跑一单"，网关可并发重试 |
| 缓存亲和路由 | 记住上次走的线路 | 同一目的地走熟路更快 | 快递不会因为"熟路"更便宜 |
```

**"不同构点"这一列是必须的**，三个作用：

1. 防止读者把类比当真相
2. 防止你自己在写作中不知不觉越界（"因为快递会丢件，所以网关也会丢件"）
3. 让内行读者看到你有边界感，信任度反而更高

## 四、类比的展开技巧

### 技巧 1：用数量级让"为什么需要"变成算术

不要说"很复杂"，把它算出来：

```
三种协议 × 二十家渠道 = 60 种适配
加一层：三种 + 二十家 = 23 种适配
```

乘法变加法，这是"为什么要有这一层"最有力的解释，比任何形容词都强。

### 技巧 2：每个环节回答三问

任何一道工序，都按这个顺序讲：

1. **外行版**：这一步在做什么（一句话，不出现术语）
2. **没它会怎样**：删掉这一步，具体坏在哪（这是说服力的来源）
3. **技术上**：机制与取舍（给内行看的）

顺序不能反。先讲技术，非技术读者第一句就掉队。

### 技巧 3：把"看不见的难点"翻成可感的画面

原文只写"字节级稳定"四个字——这是最难但最容易被忽略的地方。翻法是：

> 上游是一个字一个字吐出来的。一个中文字符在 UTF-8 里占三个字节，完全可能前两个字节在这一块、第三个在下一块。按字符串直接解码，就会变成乱码。

**具体到字节、具体到"前两个在上一块"**，读者才真的理解"稳定"两个字有多贵。

### 技巧 4：顺序即成本

如果环节有排列顺序，说明顺序本身的理由，而不是当流程念一遍：

> 先认人 → 再看会不会做 → 再看放不放得进 → 再看有没有钱 → 最后才决定去哪。越靠前的门越便宜，能挡一个是一个；最贵的一步放最后，系统才扛得住量。

## 五、自检清单

- [ ] 全文只有一个主类比，最后一节还能用它收尾
- [ ] 映射表有 6 个以上角色，且写了"不同构点"
- [ ] "为什么需要这一层"用算术/数量级讲，不是形容词
- [ ] 每个环节都有"没它会怎样"
- [ ] 至少有一处把原文的抽象词翻成具体画面（字节/秒/次数）
- [ ] 术语表里的每个名字，动态图上都有锚点
